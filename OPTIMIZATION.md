**Классификация: spike** — вопрос «что можно ускорить», на выходе рекомендации. Код я уже разобрал (это была разведка контекста); дальше — отчёт, без правок. Реализация — отдельная задача с твоего явного «да».

Наблюдение «5 GB VRAM из 24, CPU/RAM простаивают» идеально ложится на код: GPU-модели тут не бутылочное горлышко. Время жрут последовательные проходы по кадрам, диск и повторные загрузки весов. 2 секунды → 2–3 минуты — это оверхед пайплайна, а не инференс.

## Главные тормоза (по убыванию выгоды)

1. **ProPainter на полном разрешении источника** — `propainter.py:135-141` только округляет до /8, никогда не даунскейлит. RAFT (20 итераций, fp32!) + flow-completion + transformer на 1080p/4K. Официальный ProPainter считает на короткой стороне ~432–640. Даунскейл рабочего разрешения (например 720p) с апскейлом только вырезанной дырки — **одно крупнейшее ускорение, раза в 3–8 на этом этапе**.

2. **Перезагрузка весов на каждый job** — `worker.py:122` + `composition.py:283-303` собирают новые адаптеры на каждый запрос: `from_pretrained` / `torch.jit.load` заново. Для коротких роликов загрузка — существенная доля 2–3 минут. Нужен process-level warm cache моделей.

3. **SAM2 по-кадрово вместо пропагации масок** — `sam2.py:59-90` гоняет image-encoder **на каждом кадре**. `sam2-video` (`sam2_video.py`) умеет пропагацию (encoder один раз + propagation), но не дефолт. Плюс transformers-путь fp32 без autocast (`145-157`). Переключение на `sam2-video` или кэш эмбеддингов — **крупное ускорение сегментации**.

4. **Лишние JPEG-круги через диск** — раскладка всех кадров в JPEG (`run_cleanup.py:156-159`), запись всех масок в JPEG даже при `keep_workdir=false` (`316-317`), запись всех inpainted-кадров (`363-365`, verify переписывает все ещё раз `428-429`), повторное чтение для x264 (`ffmpeg.py:132-163`). Пайп сырых кадров в ffmpeg stdin + запись дампов только при `keep_workdir` убирает большую часть I/O.

5. **Verify включён по умолчанию** (`verify=True`) — это второй полный проход: detect + track + segment + возможный re-inpaint (`run_cleanup.py:370-433`), т.е. +30–80% сверху. Профиль `fast` уже доказывает, что без него можно.

6. **GroundingDINO без батчей + CPU-трекинг** — один forward на (keyframe × phrase) (`grounding_dino.py:95-108`), затем LK + CSRT + template-match **по всем кадрам отдельно на каждый трек** (`_cv.py:136-279`) с повторными grayscale/resize и промахами LRU-кэша кадров. Батчинг фраз, общие grayscale-проходы, кэширование — заметно для детекта.

7. **ProPainter: CPU-синк каждые ~5 кадров** — `.cpu().numpy()` + numpy-композитинг в `_transformer` (`propainter.py:292-309`); overlap-чанки дают ~11% лишних кадров. Плюс `.half()` модели пересоздаётся на каждый чанк (`163-164`).

8. **Прочее**: LaMa fp32 и на GPU без autocast (`lama.py:106-111`); вообще нет ни `--work-res`, ни `--frame-stride`, ни precision-переключателя, ни batch-size для детектора/сегментатора (`config.py:137-264`) — единственная «ручка скорости» это `--profile fast`.

## Что это значит для твоего сценария (ролики до минуты)

При текущей архитектуре 60 сек ≈ часы обработки. Прицел:
- **быстрые победы** (конфиг/мелкие правки, часы работы): выключить verify для скоростных прогонов, warm-cache моделей, не писать маски/дампы при `keep_workdir=false`, `sam2-video` вместо `sam2`;
- **средние** (день): `work_res` даунскейл для ProPainter/SAM2 + апскейл дырки, bf16/fp16 везде на CUDA, убрать JPEG-раундтрипы (pipe в ffmpeg), батчинг GroundingDINO;
- **архитектурные** (дни): stride/интерполяция треков для длинных видео, GPU-композитинг в ProPainter, overlap-чанки без冗余, возможно замена LaMa на per-clip подход.

Реалистично: быстрые + средние дают **порядок ускорения 5–15×**, что для минутного ролика превращает часы в ~5–15 минут. Скажи, куда двигаемся — могу оформить это в дизайн/план по приоритетам, или сначала профилировать реальный прогон на RunPod, чтобы подтвердить доли времени по этапам.
